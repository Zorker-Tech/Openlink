## Возможности

**Каждый проект — полноценное рабочее пространство.** Ему принадлежат файлы и история Git в `/workspace`, постоянная среда исполнения, инструменты разработки и отдельный серверный компонент приложения. Сеансы чата запускаются в отдельных песочницах внутри границ проекта. При использовании VM каждый проект получает отдельную гостевую Linux-систему и ядро. Режим совместимости на контейнерах предоставляет другой, явно обозначенный уровень изоляции.[Проектные VM](./docs/architecture/ADR-0007-project-vm-runtime-boundaries.md) · [Уровни изоляции](./docs/architecture/ADR-0022-production-deployment-profiles-and-resource-governance.md)

- **Создание и проверка:** работайте с агентом в чате проекта, изучайте файлы в редакторе, просматривайте результат в нативном предпросмотре или изолированном браузере Chromium.[Архитектура браузера](./docs/architecture/ADR-0004-browser-runtime-surfaces.md)
- **Собственный backend проекта:** каждая Project VM может запускать совместимые с Supabase службы Auth, PostgreSQL, Realtime, Storage и Functions. Данные и секреты отделены от управляющей базы OpenLink.[Жизненный цикл](./docs/architecture/standards/04-runtime-lifecycle.md)
- **Многопользовательская архитектура:** пользователи, организации, рабочие пространства и проекты имеют явных владельцев. Сервисы повторно проверяют права, а открытые таблицы используют построчные политики безопасности.[Данные и безопасность](./docs/architecture/standards/05-data-and-security.md)
- **Local, Cloud и база знаний:** локальный и облачный режимы используют одинаковые контракты, но раздельные учетные записи и данные. При настройке провайдера эмбеддингов доступен семантический поиск с фильтрацией по арендатору.[Компоненты системы](./docs/architecture/standards/02-system-context.md)

**Публикация проектов:** публикация созданного проекта на выбранном сервере или локальной машине одним нажатием с автоматическим назначением работающего домена пока не введена в OSS-версию. Эта возможность будет постепенно появляться в следующих выпусках OSS. Самостоятельное размещение OpenLink и предпросмотр проекта — отдельные процессы.[Установка](./docs/operations/self-hosted-installation.md)

## Начало работы

Для полного локального запуска нужны виртуализация и подготовленные компоненты среды, описанные в [руководстве разработчика](./DEVELOPMENT.md). Запуск только Web-процесса не дает всех функций приложения.

```bash
git clone https://github.com/Zorker-Tech/Openlink.git
cd Openlink
git switch oss
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env.local
# Проверьте настройки, необходимые для вашей среды.
pnpm dev:local
```

Не добавляйте учетные данные в Git. Доступные параметры перечислены в [`.env.example`](./.env.example).

## Свои изменения и обновления

Храните собственные изменения в отдельной ветке. Для нее можно создать отдельный каталог worktree:

```bash
git fetch origin
git worktree add -b my-team/openlink-custom ../Openlink-custom origin/oss
```

Если достаточно одного каталога, используйте `git switch -c my-team/openlink-custom origin/oss`. Чтобы включить последующие изменения OSS, выполните `git fetch origin`, а затем `git merge origin/oss` в своей ветке. Проверяйте конфликты и миграции: worktree не выполняет их автоматически.

## Планы

Мы планируем постепенно выделять повторно используемые компоненты OSS в SDK, расширять функциональность и публиковать инструкции по обновлению. Публикация проектов одним нажатием с подключением домена также будет постепенно вводиться в OSS. Эти планы не означают, что SDK, автоматическая миграция или полный процесс публикации доступны сейчас.
